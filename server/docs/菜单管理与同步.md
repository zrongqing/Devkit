# Web 多级菜单与同步管理

Web 页面代码通过正常 Web 发布上线；“上传菜单”只同步元数据，不接收或执行动态代码包。运行时的名称、层级、排序和启用状态来自数据库，组件始终由 Web 本地声明解析。Desktop 继续使用原配置菜单。

## 声明与稳定编码

在业务目录增加 `menu.ts`，默认导出 `directory(...)` / `page(...)` 数组（辅助函数位于 `web/src/router/menuDefinition.ts`）。统一注册器通过 `import.meta.glob` 收集声明，无需另外维护页面表和路由权限表。

- 目录：`menuCode / type=directory / parentCode / title / iconKey / order`。
- 模块：在上述字段基础上声明 `type=module / routeKey / requiredPermissions / isClosable / loader`。
- 菜单业务编码与 `routeKey` 独立；例如 `knowledge.search` 对应原路由 `study-projects`。同一组件的不同入口分别编码。移动源码、修改名称或父目录不改变编码。
- 上传排除 `loader`，目录 `routeKey=null`、业务权限为空。编码最长 120 字符，仅使用小写字母、数字及 `.`；每段必须以字母开头。禁止空段、空白、横线、下划线、首尾点。`.` 表示业务命名空间，不代表当前菜单展示层级。
- 禁止重复编码、重复模块路由、模块包含子节点、目录绑定页面、缺失父目录或循环；最多 32 层。同步后编码、类型和模块路由不可修改。

目录点击仅展开、收起；模块点击打开对应页签。Web 丢弃当前构建未提供的模块，并移除没有可访问子模块的目录。导航和直接路由采用同一访问规则，刷新菜单会关闭失去访问权的页签。顶部导航显示按钮保留图标收起和完全隐藏两种模式。

## 管理与同步

“系统管理 / 菜单管理”提供菜单配置和前端菜单对比两个页签。配置支持创建目录、编辑展示字段及删除空目录；模块只能通过声明同步创建。停用目录隐藏整棵子树，配置与授权保留。首页、菜单管理及其有效祖先路径受到保护。

对比按编码返回 `new`（未同步）、`synced`（已同步）、`changed`（声明变化）、`missing`（当前 Web 缺失）、`manual`（后台自建目录）。详情显示前端默认值、上次同步声明与数据库当前配置；“已同步”不表示后台展示配置必须等于前端默认值。

同步选中的新菜单时自动包含未入库祖先。已有记录默认仅更新声明快照和业务权限提示；名称、父目录、图标、排序、启用状态保持后台值。可通过 `applyFields` 明确应用 `title / parentCode / iconKey / order`。启用状态只在配置页调整。新模块默认启用且仅管理员可访问，普通用户需另行授权。当前 Web 缺失的模块不会自动删除或停用。

菜单集合具有全局 `version`，记录还具有 `revision` 及审计字段。创建、编辑、删除与同步均提交所读取的全局版本。服务端在单个事务内重验完整树和版本；过期返回 HTTP 409、`code=menu_conflict`，管理员应重新比较，禁止直接以新版本重试旧覆盖操作。批次校验失败时整批回滚。

## 授权

菜单授权使用 Identity 用户、角色声明表中的 `menu:web`；业务权限仍为 `permission`。用户有效菜单权限为直接授权与角色授权并集。Administrator 拥有全部启用模块的菜单访问权；已停用的祖先仍会隐藏模块。保留原首页、基础参数和关于 Web 的公开属性，公开页面无需显式授权。

只给模块授权；界面勾选目录是批量选择模块，不写目录声明。用户/角色界面分别配置业务权限及菜单权限，并提示所选页面缺少的业务权限。仅有菜单权限的用户可以打开页面受限提示，业务组件不会挂载或自动请求已知无权访问的接口。菜单或业务授权变更都不会自动修改另一类授权。

配置、比较及同步要求 `system.menus.manage`。菜单列表也允许用户、角色、权限管理员读取以选择授权对象。用户菜单授权要求 `system.permissions.manage`；角色菜单授权要求 `system.roles.manage` 或 `system.permissions.manage`。普通授权管理员不能操作超出自己菜单范围的授权；分配角色时也检查角色菜单，避免间接越权。

## HTTP 契约

OpenAPI `/openapi/v1.json` 是正式契约，成功响应为 `{ data, traceId }`，错误为 ProblemDetails（含 `code / traceId`）。除公共导航外要求 Bearer Token。

| 方法与路径 | 请求 / 响应 data |
| --- | --- |
| GET `/api/v1/web/navigation/menus` | 返回可访问菜单数组，新增 `menuCode / type`；`id=menuCode`，`parentId=parentCode`；目录 `routeKey=""` |
| GET `/api/v1/web/menu-management/menus` | `{ version, menus: MenuView[] }`，完整数据库配置 |
| POST `/api/v1/web/menu-management/menus` | `{ version, menuCode, title, parentCode, iconKey, order }`，仅创建目录 |
| PUT `/api/v1/web/menu-management/menus/{code}` | `{ version, title, parentCode, iconKey, order, enabled }` |
| DELETE `/api/v1/web/menu-management/menus/{code}?version=N` | 仅删除空目录（软删除，不复用为另一种模块） |
| POST `/api/v1/web/menu-management/compare` | `{ menus: MenuDeclaration[] }` → `{ version, items: [{ menuCode, status, local, current }] }`，不修改配置 |
| POST `/api/v1/web/menu-management/sync` | `{ version, menus: MenuDeclaration[], items: [{ menuCode, applyFields: [] }] }` |
| PUT `/api/v1/identity/users/{id}/menus` | `{ menuCodes: string[] }` 替换用户直接菜单授权 |
| PUT `/api/v1/identity/roles/{id}/menus` | `{ menuCodes: string[] }` 替换角色菜单授权 |

`MenuView` 包含声明的展示字段，以及 `enabled / isPublic / source / revision / lastDeclaration`。用户响应新增 `menuCodes / effectiveMenuCodes`，角色响应新增 `menuCodes`，当前权限响应新增 `menuCodes`；原 `permissions / effectivePermissions` 保留。客户端变更授权后刷新权限快照与导航。Web 调用位于 `src/api/menuManagement.ts`，Desktop 示例位于 `client/templates/WorkspaceApi.http`。

## 迁移与发布

1. 发布前备份数据库，使用现有部署迁移流程执行 `20260923121446_AddWebMenuManagement`，创建 `WebMenus / WebMenuState`。不需要迁移业务项目或知识库数据。
2. 发布服务端。启动初始化器仅在 `WebMenuState.Version=0` 时将 `Navigation:Common + Web` 按新层级导入，并按已有用户/角色业务权限一次性补齐原菜单访问权。菜单管理不参与旧权限回填，默认仅 Administrator 可用。
3. 发布 Web。管理员刷新权限、导航，打开菜单管理对比声明；后续新页面由此同步并单独授权。原 routeKey 链接继续可用。

初始化与旧授权回填在同一事务提交；以后启动不会覆盖后台配置或重新授予已撤销的菜单。不要手动重置版本。`Navigation:Web` 此后只作为首次初始化默认值，新页面无需修改该服务端配置。菜单类型与路由不可原地改变，另建编码迁移授权后停用旧页面。

验证命令：`npm run build`（web）；`dotnet build server/Devkit.Server.slnx`；`dotnet test server/Devkit.Server.slnx`。接口测试使用独立 SQLite，覆盖同步、冲突、原子回滚、树校验、鉴权、授权合并与首次迁移；SQL Server 的真实锁竞争和迁移执行仍应在发布验证环境验证。
