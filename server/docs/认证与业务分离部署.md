# 认证与业务分离部署

## 代码和领域边界

Identity 与 Business 已拆为同一解决方案中的独立上下文，每个上下文各有 Api、Infrastructure、Application、Domain 四个项目。上下文内部继续遵循 Api → Infrastructure → Application → Domain；两边生产项目不互相引用，不共享业务实体、DbContext 或签名私钥。审计字段、持久化基础设施和 API 启动等技术能力放在 `server/src/Commons`，详见 [公共基础模块](公共基础模块.md)。

| 上下文 | 目录 | 职责 | 数据归属 |
| --- | --- | --- | --- |
| Identity | `server/src/Identity` | 账号、认证会话、角色、权限分配、导航和菜单授权管理 | 用户、角色、声明、刷新令牌、Web 菜单及菜单版本 |
| Business | `server/src/Business` | 备考、模块、系统运行信息 | 学习资源、业务作业、模块运行状态 |

原 `Server:Role`、Combined 模式和同一镜像按角色切换的方式已移除。IdentityDbContext 与 BusinessDbContext 分别维护模型和初始迁移；三个上下文统一使用 `ConnectionStrings:Devkit`，连接同一 SQL Server 实例中的同一个 `Devkit` 数据库，保留独立表模型和 HTTP 服务边界。

身份上下文中的权限目录是授权管理的版本化词汇；业务上下文只定义自己的能力与资源规则。业务内部 Actor 是从 HTTP 响应映射得到的本地调用者模型，没有引用身份实体。同一个用户只通过稳定用户 ID 关联两边的数据。

文件存储已进一步迁出 Business，形成第三个独立上下文 FileStorage；文件、存储与迁移任务不再由 Business 承载，配置与旧文件数据升级见 [文件服务独立部署](文件服务独立部署.md)。下文保留历史拆库流程；当前共用 `Devkit` 的部署按 [数据库与认证](数据库与认证.md) 执行，不运行拆库脚本。

## HTTP 契约与撤销行为

所有既有 HTTP 路径和响应信封保留，按宿主分布：

- Identity：`/api/v1/auth/*`、`/api/v1/identity/*`、`/api/v1/web/*`、`/api/v1/client/navigation/*`。
- FileStorage：`/api/v1/files/*`、`/api/v1/storage/*`。
- Business：备考、模块控制面以及 `/api/v1/system/*`。
- 两边各有 `/openapi/v1.json`、`/swagger`、`/health/live` 和 `/health/ready`，文档只描述各自的端点。

业务请求先本地验证 RS256 签名、签发者、受众及有效期，再携带同一个 Bearer access token 请求 Identity 的 `GET /api/v1/auth/permissions`。Identity 验证认证版本并返回当前权限。Business 检查返回的 subject 与 JWT subject 一致，映射成本地 Actor 后执行资源归属及功能权限检查。

一次业务请求只获取一次权限断言，不跨请求缓存，不读取身份数据库或身份 Redis。全部退出、密码变更、账号禁用、刷新令牌重放和角色变更等撤销行为由 Identity 执行；后续业务请求重新向它确认状态。身份服务返回 401/403 时业务请求返回 401；身份服务网络故障、超时、重定向、非成功响应或断言格式/subject 错误返回 503 `identity_unavailable` ProblemDetails，不清除有效客户端会话，也不放行业务操作。

因此当前选择是同步确认身份：Identity 不可用时，受保护业务请求也不可用。Identity 内部原有版本缓存的 TTL、失效竞态与 Redis 回退 SQL 行为仍保留；这并非跨服务强一致撤销协议。后续若需提高身份服务故障期间的可用性，应单独设计事件投影与可接受的撤销延迟。

## 配置和密钥

三个服务均使用 RSA（至少 2048 位）PEM 密钥；Identity 只配置私钥，Business 与 FileStorage 只配置公钥。验证服务若加载私钥 PEM 会拒绝启动。密钥在启动时加载，当前没有 JWKS 自动发现和多公钥重叠轮换。更换签名体系或密钥后旧 access token 需要刷新或重新登录。

两边 User Secrets 分别是 `Devkit.Identity.Api`、`Devkit.Business.Api`。外部 JSON 文件环境变量分别为 `DEVKIT_IDENTITY_CONFIG_FILE`、`DEVKIT_BUSINESS_CONFIG_FILE`；原来的 `DEVKIT_CONFIG_FILE` 和合并配置须按上下文拆开。外部文件加载后环境变量和命令行仍具有更高优先级。

Identity 需要 `Jwt:SigningPrivateKeyPath` 和自己的数据库/Redis；Business 需要 `Jwt:ValidationPublicKeyPath`、自己的数据库和 `Identity:BaseUrl`。跨主机调用默认要求 HTTPS，只有显式 `Identity:RequireHttps=false` 才接受 HTTP。示例 Compose 仅在内部网络使用 HTTP，公网入口另外配置 HTTPS。

## VS 与本地开发

参见 [Docker 发布与 Visual Studio](Docker发布与VisualStudio.md)。打开 `server/Devkit.Server.slnx`，将 `Devkit.Identity.Api`、`Devkit.FileStorage.Api` 和 `Devkit.Business.Api` 设为多个启动项目；默认监听 12512、12513 和 12511，可分别命中断点。先在同一个数据库中执行三个上下文的迁移，再启动 Identity、FileStorage 与 Business。

Web 统一设置 `VITE_API_BASE_URL=/`、`VITE_DEV_API_TARGET=http://localhost:8081`；Nginx 负责将认证、文件与业务请求分发到各自服务。VS 调试使用 `compose.development.yaml`，完整容器部署使用默认 Compose；前端无需切换三个端口。直连部署仍可显式覆盖服务地址及 CORS 源。

## Docker 发布

`compose.yaml` 默认构建并运行独立的 `devkit-identity` 与 `devkit-server`（业务）服务：

```powershell
dotnet build server/Devkit.Server.slnx
dotnet test server/Devkit.Server.slnx
npm --prefix web run build
docker compose config --quiet
docker compose up -d --build
```

先从 `.env.example` 准备本机 `.env`，填写统一数据库文件路径 `DEVKIT_DATABASE_CONFIG_FILE`、公私钥文件、文件服务密钥和已存在的数据挂载目录；一个共享 `Devkit` 数据库连接串集中于该 JSON 文件，见 [数据库与认证](数据库与认证.md)。`compose.split.yaml` 仅作为空兼容覆盖文件保留，旧的双文件 Compose 命令仍可使用。

默认 Web 网关 8081、业务 8080、认证 8082、文件 8083。Identity 镜像包含身份上下文及所需公共程序集，Business 镜像包含业务上下文及所需公共程序集；Dockerfile 分别位于对应 API 目录。`.env` 可分别指定镜像与版本；`Publish-Server.ps1 -Context Identity|Business|FileStorage` 也可单独构建。GitHub Release 支持 `identity-v*`、`business-v*` 独立发布，`filestorage-v*` 独立发布，以及 `server-v*` 同时发布三个镜像；镜像互不包含对方上下文的程序集。

## 历史独立数据库部署的拆库流程（共库部署不执行）

新初始迁移不应直接应用到旧合并数据库。此次代码变更不会自动迁移或操作现有数据。

1. 备份旧数据库、文件对象和外部索引，在隔离预发布环境演练。旧数据库应先升级到拆分前最后一个迁移；旧迁移源文件保存在 `server/legacy`，实际旧版本升级使用对应 Git 版本的工具。
2. 创建两个空目标数据库，分别运行 `Update-Database.ps1 -Context Identity` 和 `-Context Business`，不要使用 `-SeedBootstrapAccount`，也不要先启动新服务。
3. 停止旧应用及新服务。使用具有源读取、目标写入权限的维护账号，在同一 SQL Server 实例执行：

```powershell
sqlcmd -S localhost -E -b -i server/scripts/Split-LegacyDatabase.sql -v LegacyDatabase="DevkitLegacy" IdentityDatabase="DevkitIdentity" BusinessDatabase="DevkitBusiness"
```

4. SQL 脚本在事务中按外键顺序复制 27 张表，保留用户 ID、密码哈希、角色授权、资源 ID、审计字段和软删除状态。源数据及迁移历史不变，两个目标各自保留新迁移历史；目标已有业务数据时脚本拒绝执行。该脚本需要 SQL Server 2022 / SQLCMD，不能在 SQLite 或 Azure SQL 的独立数据库间直接运行。
5. 核对各表行数、账号权限、文件引用和抽样业务记录。迁移文件对象时保留对象键；若运行平台/存储根目录改变，另外完成文件和 StorageLocations 路径迁移。Qdrant 索引需要保留或重建，SQL 脚本不复制磁盘对象与外部索引。
6. 继续执行 [文件库拆分](文件服务独立部署.md) 中的离线复制。配置三个受限应用数据库账号、RSA 密钥及服务密钥，启动 Identity、FileStorage、Business，再开放网关。旧签名令牌需要重新登录或刷新。

实际业务数据迁移需在预发布环境独立验证；当前自动测试使用三个隔离 SQLite 数据库，不代替 SQL Server 数据升级演练。源库应保留以便回滚；新系统产生新数据后，回滚还需另外处理增量数据，不能直接切回旧库。

## Desktop 兼容性

此次未修改 Desktop。已有客户端的 `DEVKIT_API_BASE_URL` 应指向统一网关 8081；直接指向业务端口将无法登录或获取导航。若以后要求 Desktop 直连两个服务，再单独修改客户端范围。
