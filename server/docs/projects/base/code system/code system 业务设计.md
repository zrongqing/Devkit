# 编码规则系统需求与业务设计

**目标**　各业务模块可以为单据、批次和主数据定义编码规则。业务人员能读懂编码，系统能用稳定的业务对象 ID 找回第一次生成的编码。例如，入库单号 `RK-20261110-0001-A` 依次包含单据前缀、业务日期、当天的四位流水号和后缀。

**文档状态**　首版已实现，入口为 Web 工作台的「系统管理 → 编码规则」。本文定义业务行为，[数据库与发号事务](数据库与发号事务.md)定义持久化与并发约束，[接口与验收](接口与验收.md)列出已实现的管理契约和可复核的验收场景。实际接入以服务端发布的版本化 HTTP 契约与 OpenAPI 为准。

## 1. 适用范围与首版口径

编码系统当前按 **Business 服务内的业务模块**设计。编码管理、后台初始化和正式发号都在 Business 内执行。用户及角色由 Application 身份服务管理。

原始需求覆盖全系统业务编码的规则配置，支持前缀、后缀、自增序号以及可拆开的年、月、日。各业务场景通过稳定规则键接入，例如 `wms.receipt` 表示入库单，`master.material` 表示物料。业务对象继续使用自己的内部主键，修改名称、撤销单据或重印标签都沿用首次生成的编码。

| 评审项 | 首版设计假设 | 对使用方的影响 |
| --- | --- | --- |
| 唯一范围 | 一条规则内，最终编码在全部期间和全部版本中唯一 | 跨规则定位使用“规则键 + 编码”。同一业务唯一列绑定一条规则。若扫码入口只传裸码，接入模块须预先划分互不重叠的前缀 |
| 流水归属 | 一条规则在一个期间共用一个计数器 | 同一规则下多个仓库共同计数。需要独立前缀和流水的场景分别登记规则 |
| 业务日期 | 按服务端正式取号时刻换算，首版统一采用固定偏移 `UTC+08:00` 和公历 | 跨午夜以取号事务中选定的时刻为准。补录、回填单据日期沿用这条口径 |
| 连续性 | 成功签发的号码永久占用，接受业务单据之间出现空号 | 调用方超时可找回原号。单据作废、下游保存失败均不释放号码 |
| 接入方式 | 首版在线、单对象、单次取号。Business 为业务提交动作登记规则键和对象类型 | 网页展示预览。经办人正式提交单据时，由 Business 在完成单据授权后调用内部发号逻辑 |

## 2. 使用者与操作权限

### 管理员首次使用

1. 按[数据库部署与配置](数据库与发号事务.md)执行迁移，启动更新后的 Application、Business 并发布 Web。Application 首次启动或升级时会补齐「系统管理 → 编码规则」（`system.coderules`）。admin 刷新页面即可看到启用的入口。若已由管理员停用，可在菜单管理查看并调整。普通用户需要相应菜单授权与模块业务权限。
2. 进入「系统管理 → 编码规则」，选择「新建规则」。开发环境从入库单、批次、物料三个场景选择；生产默认没有场景，部署者先登记允许使用的规则键。
3. 以入库单为例，选择 `wms.receipt`，输入业务名称，保留四位流水，添加固定文本 `RK-` 并上移。保持全程累计，样例序号输入 1，点击「预览编码」可见 `RK-0001`。保存草稿后核对生效定义和草稿，填写原因并发布。历史版本显示本次发布的完整定义，有审计权的用户在变更记录看到原因。
4. 需要正式号码的 Business 模块在业务提交动作中先校验对象访问权，再调用 `ICodeGenerator.IssueAsync(ruleKey, requestId, businessId, actorId, ct)`。只有签发成功后才绑定返回的 `IssueId` 和 `Code`。场景示例可供配置和联调，生产单据动作由实际接入的模块负责。

### 岗位分工

| 使用者 | 操作和数据范围 |
| --- | --- |
| 规则维护员 | 在获授权模块创建规则、修改草稿、调整段顺序、预览样例、核对当前生效版本 |
| 规则发布员 | 在获授权模块审阅草稿相对当前版本的差异，发布、停用和恢复，填写变更原因。维护与发布权限可按业务岗位分别授予 |
| 业务经办人 | 在原有业务页面提交有权操作的单据，查看返回的正式编号。保存草稿或刷新页面均不触发取号 |
| 授权审计员 | 查询获授权模块的全模块发号流水、版本和变更记录，可按编码反查签发时刻、版本和对象 ID。打开业务单据仍由所属模块校验访问权 |

### Business 启动时的后台初始化

每次 Business 启动后，编码系统在独立的后台任务中依次检查角色和基础数据。初始化清单随版本维护，每项声明稳定键、初始值和执行顺序。上表中的岗位说明权限分工，部署需要的预置角色以已登记的清单为准。

| 顺序 | 检查项 | 缺失时如何处理 |
| --- | --- | --- |
| 1 | 编码系统预置角色 | Business 请求 Application 核对已登记的角色。Application 自动创建缺失角色及其初始权限，已有角色保留当前配置。用户与角色的分配由授权管理员办理，业务经办人沿用所属业务的单据权限 |
| 2 | 编码基础数据 | Business 按清单顺序和业务唯一键逐项检查，在本地事务中创建缺项，保留已配置的数据。计数器和签发流水均在正式取号时产生 |

某一步尚无已确定的条目时，保留该步骤，以空清单完成并继续下一步。后续确认一项就将其按依赖顺序加入清单，下次启动自动补建。文中的入库单、批次和物料编码仅作示例。重启或多实例同时启动均只补缺，管理员已修改的数据、权限以及已签发的号码均予保留。

## 3. 如何定义规则

**规则头**包括唯一规则键、归属模块、业务名称。规则键采用小写字母开头，后续允许小写字母、数字、点、下划线和连字符，总长 1–64，归属模块由服务端登记关系确定。创建后键与归属固定。一个规则键永久绑定一种业务对象语义。

**规则定义**是一组按数组位置从左到右拼接的段，允许 1–16 段。以下枚举即首版编辑器选项。

| 段类型 | 配置及校验 | 示例输出 |
| --- | --- | --- |
| 固定文本 `literal` | 每段 1–32 位 ASCII 大写字母、数字、连字符、下划线、点或斜杠；大小写按输入校验。前缀、后缀和分隔符都用此类型 | `RK-`、`/A` |
| 年 `year` | 四位公历年份 | `2026` |
| 月 `month` | 两位，左侧补零 | `03` |
| 日 `day` | 两位，左侧补零 | `07` |
| 流水 `sequence` | 有且仅有一段，十进制定宽 1–12 位，左侧补零 | 宽度 4 时，数值 7 输出 `0007` |

序号起值和步长均为正整数，默认各为 1，均不得超过当前宽度的最大值。期间第一笔取起值，以后每笔在最近一次成功值上加步长。定宽溢出时整笔失败。所有段的输出长度合计上限为 64；日期段可单独出现、自由排列，各类型至多一次。模板只接受表内定义的结构和参数。草稿保存、预览、发布均执行完整校验，错误定位到段序号或配置字段。

| 重置周期 `reset` | 期间键举例 | 编码必须含有的日期段 |
| --- | --- | --- |
| `none` 全程累计 | `ALL` | 无必需日期段 |
| `year` 每年 | `2026` | 年 |
| `month` 每月 | `202611` | 年、月 |
| `day` 每日 | `20261110` | 年、月、日 |

期间由同一取号时刻派生，首次进入该期间时自动建计数器。强制显示完整期间能防止同一模板在下一期间从起值重发同一文本。日期段也可以只用于展示，例如终身累计的物料码可只显示年份。

| 场景 | 段顺序 | 配置与结果 |
| --- | --- | --- |
| 入库单按天编号 | `RK-` 年 月 日 `-` 流水 `-A` | 起值 1、步长 1、宽 4。11 月 10 日依次签发 `RK-20261110-0001-A`、`RK-20261110-0002-A`，次日首笔为 `RK-20261111-0001-A` |
| 按月登记批次 | `LOT/` 年 `/` 月 `/` 流水 | 起值 10、步长 5、宽 3。2026 年 3 月起为 `LOT/2026/03/010`、`LOT/2026/03/015` |
| 全程累计物料 | `MAT-` 流水 | 起值 1、宽 6。跨年时从 `MAT-000099` 继续到 `MAT-000100` |

## 4. 配置、发布与停用

1. **创建。** 维护员从获授权的登记场景中选择规则键，输入名称、段、起值、步长与周期。保存后状态为“未发布”，保留一份共享草稿。
2. **试排。** 编辑器按输入的样例时刻和样例序号生成完整编码，并标为“预览”。支持调整段顺序、比较跨日样例；预览不占号，不承诺下一个实际号码。
3. **首发。** 发布员核对差异并提交原因。一次事务生成不可变版本 1、更新当前版本、清除草稿并启用规则。此后起值、步长与重置周期固定；变更计数口径须登记新规则并安排业务切换。
4. **改版。** 从当前版本复制草稿，可调整固定文本、日期排列与位宽。新位宽必须大于或等于生效位宽。保存草稿期间原版本继续服务。发布后版本号加一，同期间沿用原计数器；历史流水始终指向签发时的版本。需要恢复旧版样式时，将兼容的历史定义复制为新草稿并按同一流程发布。
5. **停用与恢复。** 发布员填写原因后可将已启用规则停用；停用拒绝新取号，已提交请求仍可按原键找回。停用期间可编辑、发布，发布后仍保持停用，须显式恢复。恢复后同期间接续原流水。规则、版本和发号历史均保留。

规则列表显示规则键、名称、模块、运行状态、当前版本和最后修改时间；详情分别展示当前定义、待发布草稿、历史版本、变更原因。管理写操作携带读取时的修订号，冲突后刷新并重新对照差异。发号失败时业务页保留单据输入，可凭原请求重试。

## 5. 从一次提交到一次签发

以入库单为例，经办人点击提交。Business 校验其对该单据的操作权和单据状态，保存稳定的单据 ID 与取号请求 ID，按业务动作选定 `wms.receipt` 并在进程内调用发号逻辑。签发事务记录经办人 ID、版本、期间和正式编码。Business 随后以条件更新将签发 ID 和编码绑定到原单据，再完成提交。重复点击和响应丢失后的重试沿用原请求记录，重新校验单据权限。

假设 11 月 10 日当天已有两张入库单，第三笔取得 `RK-20261110-0003-A`。若网络中断，经办人在次日重试仍找回这个号码及原版本、原日期。若随后撤销该单，此号仍可追溯；次日另一张新单取得 `RK-20261111-0001-A`。单据取消或无法完成时，由所属业务模块保留原因，并按对象 ID 对账。发号流水记录已签发的号码，业务模块记录单据状态。

首个接入模块上线前须确认编号字段长度与字符集、现有数据的唯一范围、存量编号及停用旧发号器的时点。可为新规则划分与存量完全不相交的前缀；若有重叠，先完成存量核对与承接方案，再开放正式取号。历史单据保留原编号。

## 6. 独立服务如何复用编码

Business 统一管理规则并签发号码。同一进程内的业务模块直接调用 Business 的发号应用服务。FileStorage 等独立部署的服务有明确的编号场景后，通过 Business 的版本化内部 HTTP 接口调用同一个发号应用服务。`sys_code_*` 表、计数器及其迁移均由 Business 维护。

例如，假设文件归档时需要展示档案号 `DA-2026-000123`。FileStorage 继续以稳定的 `fileId` 标识文件，在归档动作中校验经办人的文件权限，再申请档案号。只有归档需要取号，上传、下载及已有文件引用仍使用 `fileId`。Business 暂时不可用时，FileStorage 保留待完成的归档请求，经办人重试后可继续绑定原号。

文件归档是候选场景，接入时再登记规则和允许调用它的服务。服务身份只限定内部接口的调用范围，岗位清单沿用第 2 节。调用与重试约定见[接口与验收](接口与验收.md)。
