# 编码规则接口与验收

配合[业务设计](code%20system%20业务设计.md)和[数据库与发号事务](数据库与发号事务.md)阅读。下列管理端点已在 Business 实现。Web 使用 `/api/v1/code-system`，调试时可在 Business 的 `/openapi/v1.json` 查看实际 HTTP 契约。

## 1. 接口及授权

Business 管理接口前缀为 `/api/v1/code-system`。权限编码为 `code.scope.{moduleKey}.{action}`，动作分别为 `view`、`edit`、`publish`、`audit`。有效的模块动作会派生对应模块的读取权及菜单能力 `code.rules.view`。授权按“模块、动作”成对配置，维护、发布、审计岗位同时获得对应模块的读取能力。例如某人可以发布 WMS 规则、只读物料规则，查询发布范围时仅包含 WMS。Business 验证 JWT 与身份权限断言，由服务端根据动作取得该人的模块范围。

接入业务时，在 Business 登记规则键、归属模块、业务对象类型以及触发签发的单据动作。维护员和发布员按各自权限管理已登记场景的编码格式。业务经办人使用原单据入口提交，Business 从已验证的用户上下文取得经办人 ID，从动作映射确定规则。

| 方法与相对路径 | 权限 | 输入与成功结果 |
| --- | --- | --- |
| `POST /scenarios/query` | 读取 | 对授权的接入目录使用 `PageQuery`，返回 `ruleKey, moduleKey, objectType`，供选择器独立加载 |
| `POST /rules/query` | 读取 | 分页查询规则摘要 |
| `POST /rules` | 维护 | `{ruleKey, name, definition}`，保存合法草稿。返回 201、规则 ID 和修订号 |
| `GET /rules/{id}` | 读取 | 规则摘要、修订号、生效定义和草稿；尚未发布或暂无草稿时，对应定义为 null |
| `PUT /rules/{id}/draft` | 维护 | `{expectedRevision, definition}` 整份替换当前草稿，返回新修订号 |
| `POST /preview` | 读取 | `{ruleKey, definition, sampleAt, sampleValue}`，按授权场景校验并渲染。返回 `{code, periodKey}`；可在首次保存前试排 |
| `POST /rules/{id}/publish` | 发布 | `{expectedRevision, reason}` 发布当前草稿，返回当前版本号、状态、新修订号 |
| `POST /rules/{id}/disable`、`POST /rules/{id}/enable` | 发布 | `{expectedRevision, reason}` 停用或恢复，返回状态及新修订号 |
| `POST /rules/{id}/versions/query`、`GET /rules/{id}/versions/{versionNo}` | 读取 | 列表按版本分页；详情返回完整快照、发布人、时刻和原因 |
| `POST /rules/{id}/issues/query`、`POST /rules/{id}/events/query` | 审计 | 分别按一笔签发、一笔配置变更分页，可反查对象与版本 |

`definition` 的完整结构见[版本快照示例](数据库与发号事务.md)。`sampleAt` 须为含偏移的 ISO 8601 时刻，`sampleValue` 为正整数且适合当前位宽。预览直接使用样例数值，既不读取计数器也不落库。服务端拒绝未知段、未知参数、额外的调用人或业务日期等覆盖字段。已发布规则保存草稿和重新发布时均校验计数策略与位宽兼容性。所有管理写入除创建外都校验 `expectedRevision`；无草稿不可发布，只有启用状态可停用，只有停用状态可恢复。

### 单据提交中的正式取号

管理写入的成功响应为 `ApiResponse<{id, revision, status, activeVersionNo}>`。规则详情返回 `{rule, revision, active, draft}`，其中 `rule` 是列表摘要。版本详情返回 `{version, definition, reason}`。校验定义失败时，ProblemDetails 的 `field` 指向配置位置。初始化草稿使用专用审计标识，人工维护、发布及签发记录稳定用户 ID。

### FileStorage 跨服务取号（后续接入）

首次接入独立服务时，可在 Business 增加内部端点 `POST /api/v1/internal/code-system/rules/{ruleKey}/issues`。请求体沿用上例的 `requestId` 和 `businessId`，首次签发返回 201，重放返回 200，两者用 `ApiResponse` 包装同一签发结果。端点调用 Business 原有发号应用服务，沿用相同的事务、唯一键和 ProblemDetails。内部端点只供服务直连，公网网关不代理。可参考[文件服务独立部署](../../../文件服务独立部署.md)中的内部调用约定。

以用户发起文件归档、每份文件使用一个档案号为例：

1. FileStorage 校验用户对目标文件的归档权限，在本地事务中为该文件创建或复用待完成请求，保存 `fileId` 和稳定的 `requestId`。事务提交后才发起 HTTP 调用，用 `fileId` 作为 `businessId`。
2. FileStorage 使用本服务的调用凭据并传递本次有效的用户身份。Business 校验服务凭据、允许的规则键（例如 `filestorage.archive`）与用户身份，从验证结果取得 `issued_by`。取号及重放均先鉴权。归档对象权限由 FileStorage 负责，Business 发号过程中无需回调文件服务。服务凭据仅授予指定规则的发号能力。
3. FileStorage 在本地事务中保存 `issueId` 和档案号，标记归档完成。超时、响应丢失或本地绑定失败时保留待完成请求，下一次授权提交复用同一对 ID。用户身份过期时重新登录后继续，待完成记录只保存业务标识。Business 不可用时，已完成归档的号码可从文件元数据读取。

接入验收需验证两个跨服务场景。其一，Business 已提交但响应丢失，FileStorage 重启后同一文件重试只绑定一笔签发。其二，FileStorage 使用有效凭据请求其他模块的规则、仅凭用户身份访问内部端点、或用户失去文件归档权后重试，均无法取得号码。上述端点与归档流程在该业务场景确认后实施。

### 查询字段与页面行为

业务表全部接入 `IPagedQueryStore` / `PagedDbContext.PageAsync<T>`，含复合主键；调用方必须传入授权范围并保留适用的软删除过滤。计数器仅用于内部查询。公开列表在服务器对 DTO 白名单执行过滤、计数、排序和分页。下列字段可筛选、排序；版本定义和草稿 JSON 仅在授权详情返回。

| 列表 | 可查询字段 | 默认顺序（末列补齐唯一键） |
| --- | --- | --- |
| 场景候选 | `ruleKey, moduleKey, objectType` | `ruleKey asc` |
| 规则 | `id, ruleKey, name, moduleKey, status, activeVersionNo, updatedAtUtc` | `updatedAtUtc desc, id asc` |
| 指定规则的版本 | `versionNo, publishedBy, publishedAtUtc` | `versionNo desc` |
| 指定规则的流水 | `issueId, businessId, code, versionNo, periodKey, sequenceValue, issuedBy, issuedAtUtc` | `issuedAtUtc desc, issueId asc` |
| 指定规则的事件 | `id, action, revision, versionNo, actorId, occurredAtUtc, reason` | `occurredAtUtc desc, id asc` |

列表请求与响应沿用 `PageQuery` / `ApiResponse<PageResult<T>>`，从第 1 页开始，默认 20 条，上限 100 条，最多 32 个条件、8 个排序字段。状态、动作使用 `PageQueries.WithOptions` 注册原始编码；关联 ID 按稳定 ID 匹配，标量多选用 `in`（同列 OR），多个条件 AND。单值 `value` 与多值 `values` 互斥，后者允许 1–100 项；日期范围用 `gte/lte`。即使授权集为空也先校验字段、类型与操作符。页外请求返回真实总数和空页。Web 列头一次提交所有列条件和有序排序，枚举显示与筛选共用字典，候选独立于当前页。详见[统一分页查询](../../../统一分页查询.md)。

### 错误与调用方动作

失败使用 ProblemDetails，包含 `status`、`title`、稳定的 `code` 和 `traceId`。校验错误另附字段路径，例如 `segments[3]`。示例：

```json
{
  "status": 409,
  "title": "本期间流水号已达到当前位宽上限。",
  "code": "sequence_exhausted",
  "traceId": "example-trace"
}
```

| HTTP / 错误码 | 条件与调用方动作 |
| --- | --- |
| 400 `invalid_request`、`invalid_rule`、`invalid_query` | 参数、规则定义或查询条件无效；按字段修正后提交 |
| 401 `unauthorized`、403 `forbidden` | 缺失或无效身份返回 401；已认证但无操作能力返回 403。先校验操作能力再定位资源 |
| 404 `rule_not_found`、`scenario_not_found`、`version_not_found` | 目标不存在或位于授权范围之外，响应不披露其他模块的配置 |
| 409 `rule_key_exists`、`revision_conflict`、`invalid_rule_state` | 场景已创建、修订号过期、首发前取号或非法管理状态转换；刷新详情并核对 |
| 409 `rule_disabled`、`sequence_exhausted`、`code_collision` | 停用、耗尽或文本冲突使新签发失败。业务方保留原请求，联系发布员处理 |
| 409 `idempotency_conflict`、`business_already_numbered` | 相同请求 ID 绑定了不同对象，或同一对象另用请求 ID。核对本地请求与对象绑定 |
| 503 `dependency_unavailable` | 事务重试用尽或存储不可用。以原请求 ID 退避重试；无响应、提交结果未知也使用原请求 ID |

## 2. 验收用例

每行从独立的规则和数据开始。用例中的“流水数”指签发记录行数。开发时在 `server/tests` 落实领域、契约及数据库集成用例，使用隔离数据库与可控时钟；涉及生产锁行为的场景须用独立 SQL Server 连接模拟不同实例。

| 编号 | 操作 | 可复核结果 |
| --- | --- | --- |
| AC01 分段与预览 | 用入库单样例、样例时刻 `2026-03-07T09:00:00+08:00`、样例序号 7 预览两次 | 均为 `RK-20260307-0007-A`，无计数器和流水；首发后同日第一笔仍为 `0001` |
| AC02 定义校验 | 分别提交零个或两个流水段、月重置缺年份、未知段、空固定文本、步长 0、13 位宽、总长 65 | 各返回 400 `invalid_rule` 及对应字段；草稿、版本和修订号均无变化 |
| AC03 周期边界 | 在 `2026-11-09T15:59:59Z` 与随后一秒按日签发；另以月规则覆盖月末，以年规则覆盖跨年，以 `none` 规则跨年 | 日规则分别属于 11 月 9 日和 10 日，各取起值；月、年规则只在各自边界重置，全程累计规则继续递增 |
| AC04 签发与补零 | 按月规则以起值 10、步长 5、宽 3 签发两个对象 | 得到 `010`、`015`；当前期间计数值 15，两笔均可按编码找回对象 |
| AC05 并发首号 | 两个实例并行提交同一新期间的 100 个不同对象及请求，各自完成可重试错误的原键重试 | 起值和步长为 1 时，100 条流水恰好覆盖 1–100，一个计数器为 100，编码无重复 |
| AC06 重放与键冲突 | 两实例同时提交同一对 ID；模拟首次响应丢失；再分别改对象 ID、改请求 ID | 所有成功响应的签发 ID、编码、时刻相同；两类改键分别得 409 `idempotency_conflict`、`business_already_numbered`，库中仍一笔 |
| AC07 草稿、发布竞争 | 已签至 7，保存更宽草稿；验证发布前取号仍使用旧宽度；同时发布并另发一笔 | 版本与实际文本始终对应同一快照；序号接续。使用旧修订号覆盖草稿返回 409，发布历史能还原旧样式 |
| AC08 停用与恢复 | 签发后停用，在停用期发布兼容版本；以旧请求重放和以新对象取号，再在同一期间恢复 | 旧请求返回原号，新对象得到 409 `rule_disabled`；发布后仍停用。恢复后取下一数值，事件可查操作人与原因 |
| AC09 定宽耗尽 | 宽 2、起值 99、步长 1，签发两笔；扩到 3 位后重试失败的那笔 | 首笔 `99`；第二笔 409 `sequence_exhausted`，计数仍为 99。重试给出 `100` |
| AC10 历史撞码 | 全程累计、宽 1。版本 1 用“流水 + 固定文本 2”签出 `12`；版本 2 改“固定文本 1 + 流水”，下一候选仍为 `12` | 409 `code_collision`，计数停在 1；加上可区分前缀并发布后，同请求成功且流水数值为 2 |
| AC11 事务与业务恢复 | 分别在计数器写入后、数据库提交前注入异常；另模拟提交成功后业务保存失败并跨日重试 | 提交前异常回滚全部写入。提交后失败可取回原日原号并完成业务绑定，流水只保留一笔 |
| AC12 身份与越权 | 未登录访问管理端，只读用户发布，经办人提交有权操作的单据，再尝试提交或重放越权单据 | 缺失身份 401，无动作能力 403，有动作权限但目标越界 404。合法提交记录原经办人，越权提交或重放均不返回编码。审计列表及场景候选仅含已授权模块 |
| AC13 查询与契约 | 插入超过一页的规则，按模块及多状态组合筛选、两列排序后翻页；空授权集提交无效 GUID 或状态值 | 返回授权过滤后的真实总数，稳定翻页无重复；非法值 400 `invalid_query`。OpenAPI 公开版本化 DTO 与 ProblemDetails，响应中无内部请求凭据 |
| AC14 配置不可变项 | 已发布规则改起值、步长、周期或缩小位宽；两个维护员同时以同一修订号保存合法修改 | 不兼容定义返回 400 `invalid_rule`。并发修改仅一个成功，另一个 409 `revision_conflict`，事件数只增加一条 |
| AC15 首次启动与按序补建 | 在隔离环境配置一个测试角色、两项有前后依赖的测试基础数据，启动 Business 并等待后台任务完成 | Application 创建缺少的角色和初始权限，Business 按顺序创建两项本地数据。未向用户分配角色，签发流水和计数器均为空 |
| AC16 重启与多实例 | 修改已有角色权限和基础数据，保留一项缺项，同时启动两个 Business 实例 | 两次后台检查后仅新增一份缺项，已有记录 ID、人工配置和授权保持原值 |
| AC17 空清单与后续补录 | 用空清单启动；下一版本只追加一项基础数据，再启动 | 首次初始化正常完成，两类数据均无新增。下一次跳过空角色步骤并补建该数据，重复启动保持一条 |
| AC18 部分成功后恢复 | 在角色创建成功后令第一项基础数据写入失败，再恢复依赖并重启 | 日志标明失败步骤与条目，后续依赖项尚未执行；重启复用原角色，按顺序补齐数据 |

`CodeSystemTests` 验证规则渲染、跨日重放、状态转换、接口和按模块授权。`CodeStartupTests` 验证部署清单、角色边界及重启补缺。`CodeLedgerSqlServerTests` 在 Windows 创建随机命名的隔离 LocalDB 实例，执行真实迁移、100 笔并发签发、并发重放、发布竞争和事务提交前故障注入，结束后清理测试库和实例。FileStorage 的两个跨服务场景属于后续接入的验收条件。

业务模块接入时，还需用其真实单据操作验证对象级权限与号码绑定。FileStorage 归档保持后续接入状态。
