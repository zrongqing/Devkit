# 数据库与认证

Application、Business、FileStorage 是三个独立服务，共用同一 SQL Server 实例中的同一个 `Devkit` 数据库。每个服务保留自己的 DbContext、实体模型和迁移，通过 HTTP 调用其他服务；共库不授权跨服务直接访问对方的表。

共库边界、开发期基线整理与发布后的增量迁移流程见 [共库服务与 EF Core 迁移管理](共库服务与EFCore迁移管理.md)。

## 基础管理服务

Application 负责账号、角色、业务权限、菜单授权、组织架构和管理操作审计。一个职位归属一个部门，用户可跨部门兼任多个职位。任职仅表示组织关系。业务权限及菜单访问权分别由用户直接授权与角色授权合并计算。

| Web 入口 | 管理范围 |
| --- | --- |
| 系统管理 → 用户管理 | 创建、编辑和停用账号。管理员可在“已停用账号”中恢复账号及原有授权，用户需重新登录。 |
| 系统管理 → 组织架构 | 创建或调整部门、维护职位并分配人员。删除前先清理下级部门、职位及其任职。 |
| 系统监控 → 管理操作审计 | 按页查看已提交变更的操作人 ID、时间、HTTP 操作、资源路径及请求标识。每页最多 50 条。 |
| 系统监控 → 运行状态 | 分别采样 Application 与 Business 的运行时长、内存和线程等进程指标。 |

升级已应用 `20261102154500_InitialIdentityContext` 的数据库时，在部署新版服务前从仓库根目录执行 `./server/scripts/Update-Database.ps1 -Context Application`。增量迁移 `20261102163454_OrganizationAdministration` 创建四张表。旧版迁移历史的处理见下方基线说明。

新安装时默认菜单包含组织架构及管理操作审计。已有菜单数据的环境，在“菜单管理 → 前端菜单对比”中同步 `system.organization` 和 `system.monitor.audit`。向使用者分别授予菜单访问权和对应的业务权限 `system.organization.manage`、`system.audit.view`。

## 数据库对象命名

业务表采用“模块前缀 + 单数名称”，表、列、索引和约束名称统一使用小写 `snake_case`。数据库名称仍为 `Devkit`，框架内部表 `__EFMigrationsHistory` 及其列保留默认名称。

| 模块 | 表名 |
| --- | --- |
| 系统身份、权限与菜单 | `sys_user`、`sys_role`、`sys_user_role`、`sys_user_claim`、`sys_role_claim`、`sys_user_login`、`sys_user_token`、`sys_refresh_token`、`sys_menu`、`sys_menu_state` |
| 系统组织与审计（Application） | `sys_department`、`sys_position`、`sys_occupancy`、`sys_administration_event` |
| 文件存储 | `file_stored_file`、`file_reference`、`file_migration_item`、`file_storage_location`、`file_storage_job` |
| 模块运行 | `module_instance`、`module_buffered_command`、`module_command_sequence` |
| 备考 | `study_knowledge_base`、`study_source`、`study_source_version`、`study_chunk`、`study_project`、`study_question`、`study_attempt`、`study_mistake`、`study_query_history` |
| 工作区 | `workspace_job`、`workspace_file_release_outbox` |

`workspace_file_release_outbox` 是 Business 工作区的文件引用释放补偿表，不属于 FileStorage 服务。前缀表示模块归属，不改变服务边界或授予跨服务访问权限。

列名按现有属性转换，例如 `UserId` → `user_id`、`CreatedAtUtc` → `created_at_utc`、`IsDeleted` → `is_deleted`，不改写列名单复数。连续大写缩写视为一个词，例如 `IPAddress` → `ip_address`、`Sha256` → `sha256`。实体映射显式指定表名，公共 Infrastructure 的 `UseSnakeCaseDatabaseNames` 在三个 DbContext 加载配置后统一应用列、索引和约束命名。新增实体需遵循同一规则；过滤索引和原生 SQL 中的物理名称也必须同步。

主键、唯一约束、索引与外键分别使用 `pk_`、`ak_`、`ix_`、`fk_`，例如 `pk_sys_user`、`ix_sys_user_normalized_user_name`、`fk_sys_user_role_sys_user_user_id`。C# 实体、属性、DbSet、影子属性及 HTTP/JSON 契约不随数据库命名变化。

## 统一数据库配置入口

唯一连接键为 `ConnectionStrings:Devkit`。`server/database.json` 保存无凭据的本机开发默认值：

```json
{
  "ConnectionStrings": {
    "Devkit": "Server=localhost;Database=Devkit;Trusted_Connection=True;Encrypt=True;TrustServerCertificate=True"
  }
}
```

该文件由公共基础设施项目复制到 API、EF 工具的输出和发布目录，不要修改生成的副本。自定义环境在仓库外维护一份同结构 JSON，并为三个 API 及迁移工具设置相同的 `DEVKIT_DATABASE_CONFIG_FILE` 绝对路径。数据库配置优先级为：统一默认文件 → 统一外部文件 → `ConnectionStrings__Devkit` 环境变量 → `--ConnectionStrings:Devkit=...` 命令行。旧的 `ConnectionStrings:Application` / `Business` / `FileStorage` 不再读取，应将实际连接迁至统一键。

```powershell
# 初次创建目录和文件；已有文件时直接编辑，不要覆盖。
New-Item -ItemType Directory -Force 'D:/.server data/devkit/config'
Copy-Item ./server/database.json 'D:/.server data/devkit/config/database.json'
$env:DEVKIT_DATABASE_CONFIG_FILE = 'D:/.server data/devkit/config/database.json'
```

VS F5 需在启动 VS 前设置环境变量，或配置 Windows 用户环境变量后重启 VS。真实连接串不得写入仓库。运行和 EF 设计时共用连接校验：必须明确 Server、Database，拒绝附加数据库文件；无效或缺失连接、显式指定的文件不存在都会报错，校验错误不输出连接串。

Compose 的 `.env` 只配置 `DEVKIT_DATABASE_CONFIG_FILE`，将同一文件只读挂载给三个 API，不再使用三个 `DEVKIT_*_SQL_CONNECTION_STRING` 变量。容器访问宿主机 SQL Server 时，将统一文件中的 Server 改为 `host.docker.internal,1433` 并使用有权访问 `Devkit` 的 SQL 登录；文件内容不经过 Compose 插值。主机迁移工具需使用适合其网络的 Server 地址，同时指向同一个实际数据库。开发与生产应使用不同实例或独立环境配置。

## 数据库迁移

三个上下文分别维护 `Persistence/Migrations/SqlServer`，在共用的 `__EFMigrationsHistory` 中使用不同迁移 ID。依次运行以下命令，勿并发迁移；API 启动不自动执行迁移：

```powershell
./server/scripts/Update-Database.ps1 -Context Application
./server/scripts/Update-Database.ps1 -Context Business
./server/scripts/Update-Database.ps1 -Context FileStorage
# 可显式指定同一份统一配置文件：
./server/scripts/Update-Database.ps1 -Context Business -DatabaseConfigFile 'D:/.server data/devkit/config/database.json'
```

`-ConnectionString` 保留为本次命令对共享连接的覆盖。脚本恢复执行前的环境变量，不输出连接串；普通迁移不播种管理员。

当前三个上下文各保留一份初始迁移基线，仅用于全新建库，每个上下文只创建自己拥有的上述前缀表。Business 初始迁移直接创建工作区文件引用释放 outbox，不会创建或删除 FileStorage 的表。2026-11-02 整理基线时重新生成了迁移 ID；旧迁移记录不匹配新基线，不能直接运行更新命令升级已有数据库，也不能只清空迁移历史表后重跑。

FileStorage 初始迁移直接创建最终结构，`file_reference.module` 为 `nvarchar(450)`，同时创建引用和可写存储位置的过滤唯一索引。不再包含旧表接管、历史字段修补或数据转换逻辑。

### 创建用户时报 `sys_administration_event` 不存在

身份管理写操作在 `ApplicationDbContext.SaveChangesAsync` 中将管理操作审计与业务数据一同保存。因此缺少审计表会使创建用户、角色及其他管理写操作整体失败，不能通过跳过审计解决。接口正常创建用户及其审计记录的行为由 `AccountMaintenanceTests` 覆盖。

`20261102163454_OrganizationAdministration` 增量迁移创建 `sys_administration_event`、`sys_department`、`sys_position`、`sys_occupancy` 四张表。先核对当前连接目标、`__EFMigrationsHistory` 和这四张表。使用当前 Application 基线的数据库可按上面的 Application 更新命令应用该迁移。

如果数据库仍记录 `20261020135044_InitialIdentityContext` 等旧基线，直接运行通用更新命令会尝试重建已有表。对于已核对 `sys_user.id` 为 `uniqueidentifier`、四张新表均不存在且组织迁移尚未应用的数据库，可以从现有迁移生成仅包含本次增量的脚本，在隔离 SQL Server 数据库验证后应用：

```powershell
# 从仓库根目录运行；输出到临时目录，审查后通过数据库工具连接实际目标库执行。
dotnet ef migrations script 20261102154500_InitialIdentityContext 20261102163454_OrganizationAdministration `
    --idempotent --context ApplicationDbContext `
    --project server/src/Application/Devkit.Application.Infrastructure/Devkit.Application.Infrastructure.csproj `
    --startup-project server/src/Application/Devkit.Application.Api/Devkit.Application.Api.csproj `
    --output "$env:TEMP/devkit-organization-upgrade.sql"
```

这里的起始迁移用于限定生成范围，不表示已将旧库切换到新基线。脚本只增加四张表、相关约束与索引，并登记实际执行的组织迁移；不重建用户表、不删除数据、不伪造初始迁移记录。如果只缺部分表或历史记录与实表不一致，应另行核对结构，不能直接套用脚本。修复后旧基线差异仍然存在，后续通用迁移更新前需单独处理。

需要保留旧库数据时，应另行设计并验证升级方案；不要直接重跑初始迁移或删除数据库。本次代码变更不执行真实数据库删除、重建或数据迁移。`legacy` 实现及 `scripts/Split-LegacyDatabase.sql`、`scripts/Split-FileStorageDatabase.sql` 保留历史命名，仅供历史部署参考，不适用于当前命名结构，共用 `Devkit` 时不要执行这些拆库脚本。

如确需迁移时创建管理员，可在 Application 命令中明确使用 `-SeedBootstrapAccount`，并通过外部环境变量提供 `BootstrapAccount__UserName`、`BootstrapAccount__Email`、`BootstrapAccount__Password`。不得向 Business 播种身份数据。

认证协议保留 `/api/v1/auth/*` 版本路径、短期 access token、哈希存储且单次轮换的 refresh token 和 ProblemDetails 错误响应。签名统一采用 RS256，Application 仅持私钥，Business 仅持公钥；旧 HS256 配置不再适用。

业务每次受保护请求通过 `GET /api/v1/auth/permissions` 获取当前身份断言，身份服务负责检查 `auth_version` 和账号状态；业务本地执行能力及资源归属规则。业务不直读身份表或身份缓存。
